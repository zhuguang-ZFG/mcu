## 帧布局与容量

raw = version(1B) + type(1B) + sequence(2B LE) + length(2B LE) + payload(0..64B) + CRC(2B LE)。CRC-16/CCITT-FALSE 覆盖前面所有字节，检查串 123456789 的结果是 0x29B1。最大 raw 72B，COBS 编码后最多73B，加零分隔符74B。响应状态字节也占 payload 容量，不能给64字节再追加状态而越界。

COBS 把数据中的零转成块长度，真正的零只作边界。CRC 检测损坏但不是认证；序号用于匹配响应，也不是安全凭据。多字节字段显式移位，不把 C 结构体内存直接发送，否则填充和端序会变成隐藏协议。

## 状态机与恢复

EMPTY 收非零进入 COLLECT，遇零验证编码、版本、长度和 CRC；过长、超时或已知丢字节进入 DISCARD，直到一个零才回 EMPTY。丢失后的第一个合法帧可能只提供重新同步边界，所以主机连接/重试前先发额外零。100ms 间字节超时按适配层观察时间计，不声称掌握每个字节的物理到达时间。

## 背压不是加大数组就解决

TX 只有4个完整帧槽，队满丢新帧并计数；只发送底层实际接受的字节。单帧100ms未完成就放弃余部，后续先发零重新同步。F407 DMA Stream5 的 HT/TC/TE 在 HISR 的10/11/9位，不是28/29/27位；每次位置变化从上次已消费位置读起。RX丢失使解析器失步，不能拼接覆盖前后的残段。

## 两板命令实操

F407 在 code/stm32/05-framed-protocol 执行 make；S3 在 code/esp32/06-framed-protocol 执行 idf.py set-target esp32s3、build。连接3.3V USB-TTL：F407 PA9 TX/PA10 RX，S3 GPIO10 TX/GPIO11 RX，交叉接线并共地。

`python3 scripts/device-console.py info --port COMx` 查询平台与能力；`status --port COMx` 查询错误与丢弃计数。协议口不混入 printf，F407 调试走 SWD，S3 文本日志走默认控制台。安装串口依赖使用 scripts/device-console-requirements.txt。

## 自测与排查

1. 一帧分10次到达会怎样？只要没有超时，解析结果与一次到达相同。
2. 坏CRC后紧接合法帧怎样恢复？坏帧的零结束当前段，随后合法段可解析；已知transport-loss则先找额外同步零。
3. 为什么响应入队失败不应执行故障命令？否则主机看似超时，设备却已执行不可重试的操作。

没有响应先查端口/交叉接线/波特率，再查是否向二进制口发送了文本；统计丢弃不等于芯片能精确报告所有线上错误。用变换后的错误流执行生产解析器，测试任意分块、连续包、过长、CRC错误和恢复，不只测试正常包。
