# F6 轻量三件套：通知为什么比队列快

> 🎯 队列通用但有"运费"：建队列要 RAM、发送要拷贝。任务通知直接写进对方 TCB——零队列、零拷贝、一次写操作，官方数据：**快 45%、省 RAM**。一对一的通信场景，通知几乎总是更优解。

## 本章精髓

1. 任务通知=TCB 里的 32 位邮箱：`ulNotifiedValue` + 状态位——通知可直接覆盖/累加/置位，接收方带超时等待；二值信号量的所有场景它都能替代且更快。
2. 事件组=24 个标志位的"公告栏"：多任务按"任意/全部"条件等待一组位——等待多个事件（如"网络OK且SD卡OK"）是它的独门场景。
3. 软件定时器跑在"守护任务"里：回调在守护任务上下文执行——所以回调里**禁止阻塞**（一堵全部定时器停摆），周期性小任务用它代替创建真任务。

## 学习目标

- 用任务通知改写 F4 的按键→任务通信，并测量对比队列版的执行时间差。
- 用事件组实现"双键齐备才解锁"的三任务协作。
- 创建一个周期软件定时器闪灯，并说明其回调上下文与禁忌。

## 记忆锚点

::: tip 一句话记住
**通知写 TCB 一步到位，事件组是位公告栏，软定时器住守护任务——回调里只办事，不等待。**
:::

## 实物实验

- 通知版 vs 队列版"中断→任务"延迟对比（SysTick 时基打点，逻辑分析仪测两版差值）；
- 事件组双键解锁：KEY0+KEY1 都按过灯才变。

## 常见坑

- **通知当通用队列用**：通知只能一对一且容量=1（32 位）——多对多还是队列。
- **事件组位被自动清零坑**：`xClearOnExit=pdTRUE` 时第一个等到的人把位清掉，后来者永远等不到——多任务等同一位要慎用。
- **软定时器回调里 vTaskDelay**：守护任务一堵，所有定时器集体迟到——回调必须快进快出。
- **通知值覆盖丢事件**：高频通知未消费就被覆盖——计数语义用 ulNotifiedValue 累加模式。
