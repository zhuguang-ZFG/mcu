# F7 内存管理：heap_1~heap_5 对比实验

> 🎯 FreeRTOS 给了你五份"内存管理员"简历：从"只进不出的守财奴"（heap_1）到"会拼碎片的清洁工"（heap_4）再到"跨区调度的大管家"（heap_5）。选谁，取决于你的产品敢不敢承受"分配失败"与"碎片"这两件事。

## 本章精髓

1. heap_1→heap_5 的能力阶梯：只分配不释放（确定性无敌）→ 可释放不合并（碎片制造机）→ 包 libc 的 malloc（线程安全包装）→ 释放+相邻合并（碎片可控，嵌入式默认答案）→ 多区域堆（SRAM+CCM 分而治之）。
2. 碎片是时间的敌人：长期运行产品里，"现在够用"不等于"一年后还够"——heap_4 的合并 + 定期 xPortGetFreeHeapSize/最小剩余监控是续命手段。
3. 任务栈不在堆里（默认）：栈从 pvPortMalloc 出来，爆栈有独立检测（stack canary/水位）——`configCHECK_FOR_STACK_OVERFLOW` 打开它，别省。

## 学习目标

- 背出 heap_1/2/4/5 的能力差异表，并为"参数表/任务创建/图形缓冲"三个场景各选一版。
- 实测：heap_4 下交替分配释放 1000 次，记录最小剩余堆曲线，判断碎片是否失控。
- 开启栈溢出检测 hook，故意爆一个任务栈并捕获。

在工程里换 heap_2 与 heap_4 各跑一遍"1000 次随机大小分配释放"，打印 `xPortGetMinimumEverFreeHeapSize`——碎片的存在感，一条曲线见分晓。

## 记忆锚点

::: tip 一句话记住
**heap_1 只进不出，heap_4 会合并，heap_5 跨区管；碎片看曲线，爆栈靠哨兵，剩多少问 MinimumEver。**
:::

## 实物实验

- quick win 的碎片曲线对比（heap_2 vs heap_4）；
- 爆栈捕获：某任务开大局部数组，OverflowHook 打印任务名——S16 的取证流程再走一遍。

## 常见坑

- **heap_2 用于长期运行产品**：碎片无解，跑着跑着分配失败——长期产品直接 heap_4。
- **configTOTAL_HEAP_SIZE 拍脑袋**：按"任务栈总和+队列+余量 30%"算，不是越大越好（挤占 .bss）。
- **栈溢出只信 HardFault**：很多时候爆栈先踩邻居数据，静默错乱——canary 是更早的哨兵。
- **中断里 pvPortMalloc**：堆分配非原子且可能耗时——ISR 禁地，预先静态分配。
